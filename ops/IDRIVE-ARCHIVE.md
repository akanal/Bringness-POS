# Encrypted IDrive archive and nightly database backup

Owner authorized automatic document storage and backup after screenshot355 confirmed actual Netcup-IDrive bootstrap success. This package runs on the host, reusing the protected IDrive configuration. It adds no HTTP endpoint, public object URL, app credential mount, payment/issuance change or SSH permission. Existing root automation cannot install new system services: one explicit owner root-console installation is necessary.

## Exact scope
- New immutable timestamp/random cloud backup objects contain a complete PostgreSQL cluster SQL dump plus a fixed whitelist of POS/platform environment configuration and Caddy configuration. Recovery key is explicitly excluded. Files are encrypted locally with AES256-GCM before HTTPS/SSE-AES256 upload, then downloaded, hashed, authenticated/decrypted and restored to a separate temporary PostgreSQL container with no network, host mount or published port.
- pg_dumpall gives a consistent transaction per database, not a single atomic snapshot across different databases or external services. Successful restore validates SQL execution/constraints and database identities; it does not reconcile third-party payments/TSE or prove business-level cross-service recovery. No production database is restored or stopped. Recovery uses an explicit temporary PGDATA mount and removes temporary containers and anonymous volumes.
- Existing stored shop invoice-preview PDFs are copied byte-for-byte to a tenant/source/database/digest-scoped encrypted secondary archive. They remain previews, not newly issued invoices. The primary database and existing account authorization/read routes remain unchanged. Other documents/receipts remain protected inside the database backup; this does not generate original PDFs for them or provide a new customer file-upload backend.
- Every night03:15 Europe/Berlin, up to5min randomized delay, systemd runs a new backup and scans existing PDFs. Only a fully successful initial job enables the timer. Missed-backup/failure observation is through systemd/journal and root-only last-success.json; no external alert channel is configured. No deletion or remote lifecycle change.

## Recovery key protection
A fresh random runtime key is root-only and never printed. During interactive installation, the owner chooses a NEW recovery passphrase of at least20 characters, twice, at hidden prompts. It must be kept in a password manager and not sent in chat. A PBKDF2-HMAC-SHA256600000-iteration derived key encrypts the random key using AES256-GCM with fresh salt/nonce. This wrapped key is uploaded immutably under backups/recovery and read back/decrypted to verify it. The passphrase is not saved. Thus a host loss can be recovered with the IDrive account plus this passphrase; the plaintext key is neither backed up alongside data nor needed in chat. Existing runtime keys and recovery receipts are never rotated/overwritten by installation. Losing both the host key and recovery passphrase makes cloud backup data unrecoverable.

The encrypted backup format is magic BRINGNESS-IDRIVE-ARCHIVE-1 followed by12-byte nonce, ciphertext,16-byte tag; magic is authenticated AAD. Key-wrap format is BRINGNESS-RECOVERY-KEY-1,16-byte salt,12-byte nonce and48-byte AESGCM encrypted key+tag; magic is AAD. Authentication completes in a private temporary file before any plaintext is published or SQL fed to the recovery container. Recovery code is in ops/idrive-archive.py (unwrap_key/decrypt/verified_sql). Always restore to an independently approved isolated target first; never pipe unverified ciphertext to a live database.

## Capacity and operation limits
SQL/encrypted bundle input is bounded4GiB, further reduced according to available private workspace with headroom for all temporary copies. The disposable restore has1GiB memory and4GiB tmpfs limit; reaching capacity fails the backup acceptance rather than restoring production or deleting old backups. A large installation needs a separate reviewed recovery capacity plan. Jobs have bounded SDK/process/systemd timeouts, no silent retries and append-only random upload names; an interrupted attempt may leave a duplicate encrypted object. Local PDF cursor state is root-only and records completion only after upload/readback/decryption. Sensitive command outputs are suppressed. Private temp data are removed after success/failure. The service serializes against existing Netcup operations using their unchanged lock; conflicting operations fail visibly, not overlap.

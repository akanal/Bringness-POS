# Bringness AI administration

The platform administrator enters `/ai-workspace.html?admin=1` using a POS platform-admin session. AI restaurant and supplier sessions cannot access the administration endpoints.

`GET /api/ai/admin/overview` reports active participants, pending email verification, submitted and accepted advertisements, unresolved and unread delivery issues, accepted order lines with a delivery date before today in Europe/Berlin, collection exceptions and recorded audit events in the last 24 hours. Open commission is the sum of received orders' commission less documented payments, clamped at zero per order. It is not an account balance or tax invoice. The dashboard lists the earliest 25 overdue lines and links to existing administration workflows; it does not activate accounts or collect payments.

`GET /api/ai/admin/audit` accepts `q`, `actor`, `action`, `from`, `to`, `snapshot` and `before`. Dates use inclusive Berlin calendar days. Search matches the action, actor or target IDs and actor names/businesses, with literal wildcard characters. AI actor names come from the AI database; POS administrator names are separately resolved through the platform database. Missing names fall back to their IDs. The API returns at most 50 rows, a frozen maximum-ID snapshot and a next-page cursor. Refresh starts a new snapshot, preventing new inserts from moving existing pages.

Structured sensitive fields (passwords, tokens, keys, SMTP credentials, bank identifiers and mandate identifiers) are redacted in responses. Details are escaped in the browser. New account status and launch-control changes include before/after values within their existing transaction. Historical events retain their original information; missing historical values are not reconstructed. The API offers no audit editing or deleting endpoint. This is an operational log, not a cryptographically tamper-proof record; database administrators retain database access. It covers actions that existing modules record in `ai_audit`.

Validation: `node server/ai-tests/integration.mjs` exercises aggregation, permissions, date and filter validation, stable pagination, actor resolution, redaction, transaction details and browser navigation against embedded PostgreSQL and JSDOM, alongside existing AI workflows.

## Shared POS administration

The POS platform owner opens **Admin → POS & AI → AI-Verwaltung öffnen**. `/admin/ai-workspace.html` reuses the existing AI administration interface and the POS platform session on the same origin. Its admin API calls use `/api/v1/platform/ai/*`. A server-side gateway sends these requests only to the fixed HTTPS `bringness-ai.com` administration endpoint. Active platform membership and completed password change are checked on both applications. No session is put into links or query strings, no AI database is initialized in the POS process, redirects are rejected, and requests/responses/timeouts are bounded. An AI outage leaves POS administration available and shows a retry message.

The shared AI administration retains participants and launch controls, tariffs, subscriptions, fulfilment, monitoring, advertising, barcode management, commissions, settlements, collection configuration and audit pagination. **Kontrolle → Lager, Prognosen & Beschaffung** adds account-specific location, stock, scenario, forecast, event, connector and procurement-run inspection. Account search narrows the latest 200 participants; detail limits are displayed. Connector credentials and password hashes are not selected. Only already stored forecast snapshots are reported.

An active automatic procurement policy may be disabled by the platform owner. The policy row is locked, its version is incremented and an AI audit event records the acting platform administrator and before/after state in the same transaction. Repeated disablement is a no-op. This cannot enable customer purchasing permission or cancel existing orders. Procurement checkout already rechecks the policy version under the same row lock.

The POS hub shows cross-company counts and the latest 100 uploaded offline sales with pending/conflicting stock reconciliation. It explicitly distinguishes uploaded records from sales still on disconnected devices. Existing POS customer, account, license, device and audit controls remain available. This does not add an unconfigured remote desktop transport.

Verification: gateway authorization/size/origin/assets tests, PostgreSQL AI account inspection and revocation tests, JSDOM shared POS-login navigation, existing full AI integration, filesystem-persistent offline/accountant replay and POS/AI stock bridge tests.

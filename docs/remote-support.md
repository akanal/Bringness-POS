# Bringness POS remote assistance

Platform administrators use **Admin → Fernhilfe**. The device list shows Windows version, last contact, account, device status and sanitized diagnostic capabilities. A request is available only for an active device reporting support protocol 1 within two minutes. Screen/input assistance is included from client 0.2.1; permanent device consent requires client 0.2.2. Existing installers do not gain native screen/input support through a website deployment.

The customer is asked in a native dialog to decline, share the POS window only, or share the POS window and permit input. Decline is the default. Requests expire after five minutes; approved sessions last at most fifteen minutes. A separate always-on-top native window provides the stop button. Closing that window, disconnecting, changing authentication without a permanent grant, blocking a device, revoking the initiating platform membership or expiring the initiating platform session terminates access. For session-only consent, the consenting customer session must also remain valid. Session-only consent is not resumed after a desktop process restart. From client 0.2.2, an owner/admin can use the visible native **Fernhilfe → Dauerhafte Freigabe verwalten** menu to save view-only or view-and-control consent for this device. The server stores the grant with the consenting owner and an audit entry. Sessions started under that grant are automatically accepted and can resume after a process restart or a switch to a waiter login. The visible stop window remains mandatory. Stop ends the current session; revocation ends current sessions, cancels outstanding commands, removes frames and prevents future automatic sessions. Waiters cannot grant, expand or revoke permanent consent; the owner must log in to change it. Disabling the device or the consenting owner invalidates the grant.

Only the online Bringness application window is captured. Screenshots are refreshed about every two seconds at up to 1280 × 720 pixels and sent as bounded JPEGs over the existing authenticated HTTPS connection. The latest frame replaces the preceding frame; there is no screenshot history. Frames are removed at termination and by periodic cleanup. This is periodic image assistance, not fluid video or operating-system remote desktop.

Approved control supports click, short text, Enter/Tab/Backspace/Escape/arrows, scroll and reloading the register view. OS shortcuts, arbitrary JavaScript, terminal commands, filesystem operations and unbounded input are not accepted. The admin sends the displayed frame sequence; stale or out-of-bounds requests are rejected. Inputs are dispatched at most once. A missing acknowledgement remains explicitly uncertain and is never silently replayed. Native completion means the input was delivered to the register, not that a financial transaction succeeded. Normal POS roles, payments, fiscal gates and application validation still apply.

The initiating platform session is always validated. Session-only consent validates the customer's consenting owner/admin session; permanent consent validates the active consenting owner and the device grant independently of their login session. Customers cannot access another company's devices or session. A platform admin is distinct from a customer's company admin. Requests, consent, actions, acknowledgements and stops record actor/device/session information in the POS audit. Text is redacted from admin history and removed from persisted commands after acknowledgement, timeout or cancellation; it is never included in audit payloads. Diagnostic data contains only app/platform/protocol/online/license flags and optional aggregate counters, not account passwords, device keys, paths or license files.

Offline sales and the local ledger are not remotely edited. If the POS window is disconnected, minimized or not authenticated with an owner/admin account or a same-company staff account covered by a permanent grant, the session cannot continue. Updates remain in the existing protected download/release channel and still require a valid installation license. The new Windows artifact is unsigned unless real Authenticode secrets are configured; successful compilation does not constitute a signed public release or acceptance on a real customer's hardware.

Validation: `node server/ai-tests/remote-support.mjs` exercises the real PostgreSQL-backed authorization/consent/frame/dispatch/expiry/revocation/audit flows and the admin UI. `npx electron support-smoke.cjs` on Windows uses real native capture, scaled mouse/text input the native stop control, saved device consent, automatic new-session acceptance and revocation with a simulated HTTPS service and simulated affirmative customer consent. It never connects to a customer or creates a real support session. Real-device operational acceptance remains a separate check after installation.

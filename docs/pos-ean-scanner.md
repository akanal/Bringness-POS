# EAN-Scanner module

Owner-approved price: 9.99 EUR net per month, optional for either online or Windows download base. No table module is required. No existing account is activated or charged by migration. The module uses the existing owner/PIN/email-confirmation/provider-payment flow. The public price card links to protected POS module management.

`pos_product_barcodes` assigns validated EAN/GTIN 8/12/13/14 digit strings to products within one restaurant. Leading zeros are preserved and the check digit is verified. A product may have several codes, but a code has one product per restaurant. Assignment requires current owner/admin rights, the existing administrative unlock, an active base and an active EAN module. Conflicting or concurrent assignments roll back, including any newly inserted product. All assignments are audited. There is no external product catalogue or inferred product price.

The POS exposes a dedicated scan input for keyboard-wedge scanners ending with Enter. A known available product is added to the ordinary cart; another scan increases quantity. Unknown codes offer explicit new-product entry (name, gross selling price, tax) or assignment to an existing product. Saving an assignment does not sell the item. The current checkout, payment, stock and receipt handling remains in use. Inactive/unavailable products and expired entitlements are rejected by the server. Switching restaurant while an asynchronous scan or assignment is in progress cannot silently add an item to the other cart.

Offline catalogues include saved barcode mappings only for an active EAN module. The EAN validity is capped by both the catalogue/device lease and the module's current validity/grace. The native offline UI adds known products using the immutable catalogue price. Unknown codes require online assignment and synchronisation; offline article creation is not offered. Regular offline cash sales and their replay semantics remain unchanged.

Verification uses synthetic PGlite/JSDOM fixtures: tenant/role/PIN boundaries, validated codes and leading zeros, duplicate rollback, expiry, unavailable items, repeated online/offline scans, unknown codes, explicit prices, catalogue mappings and module expiry, and both price/licensing cards. Root 506 tests and the existing full AI integration, offline/accountant and HTTP recovery suites passed locally. CI runs the new suites before Netcup deployment. No customer product, mail, purchase or payment was generated by these tests.

Scanner hardware acceptance remains to be performed with an actual keyboard-wedge device. Native offline changes require an updated Windows installer; unsigned CI test builds are not a signed public release. No installer signing or release guarantee is implied by the web deployment.

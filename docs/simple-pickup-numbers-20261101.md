# Short pickup numbers
Owner approved consecutive public labels 001, 002, 003 on handset, POS, kitchen and TV. New orders receive a durable restaurant-scoped bigint from an atomic database upsert in a BEFORE INSERT trigger. Business-day reset is requested transactionally by the existing cash-session close. The day is the session opening date in Europe/Berlin, so an overnight session stays together and repeated shift closings on the same date cannot reset twice. On the next order, numbering restarts at 001 only after earlier numbered orders are collected/served/cancelled or outside the existing 24h display window. Without a cash closing, numbering continues; no guessed midnight/cutoff reset. Within a period 1000 follows 999. Period-scoped uniqueness preserves all previous numbers. UUIDs and request capabilities remain identifiers and access controls. Cancelled/paid numbers are not recycled. Existing orders retain their old labels, avoiding renumbering already issued tickets/receipts. All new POS/table/QR orders share the same counter (gaps in the public queue are expected). No order/payment/receipt deletion or invoice-number change.

Server creation and idempotent replay return the same public number; collection polling/guest push, shared display and protected queues use the persisted value. Legacy rows use the previous UUID prefix. Guest capabilities remain mandatory; a short number never authorizes an order lookup. Actual-handler display and guest regressions cover 042; native player fixtures exercise 042 at both orientations. Database tests cover isolated counters, rollback, repeated migration, unique inserts and numbers beyond 999. Dedicated PostgreSQL CI tests 60 simultaneous inserts.
